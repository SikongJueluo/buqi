# 文档地图与写作约定

本文帮助维护者和 Agent 按任务查找资料，并决定新内容放在哪里、如何维护。

## 按任务阅读

| 任务 | 入口 |
| --- | --- |
| 了解项目定位、总体架构或当前进度 | [项目首页](../README.md) |
| 准备环境、修改代码、选择 just 任务或执行验证 | [开发指南](DEVELOPMENT.md) |
| 修改某个 crate 或 SDK，判断代码归属 | [开发指南：模块职责与边界](DEVELOPMENT.md#模块职责与边界) |
| 启动网关、配置监听地址或排查 DDS 启动 | [网关启动与配置](gateway.md) |
| 调研 Server 启动、监听地址输出与可达性边界 | [Server 网络调研](server-network-research.md) |
| 作为 Agent 开始工作，确认阅读入口与操作边界 | [AGENTS.md](../AGENTS.md) |
| 新增、拆分或重组文档 | 本文的组织与写作约定 |

这里维护入口与专题，不枚举每个包内的 README，也不列尚未创建的文档。
新增独立专题时，补充适用任务和链接，让读者知道何时需要阅读。

## 内容归属

- **项目首页**：定位、动机、总体架构、当前状态与使用入口。
- **开发指南**：环境、开发任务、模块边界和验证方法。
- **本文**：文档导航、内容放置与维护约定。
- **AGENTS.md**：面向 Agent 的阅读指针、项目特有约束与操作边界。
- **专题文档**：独立主题的详细原理、配置、步骤或证据，由相关入口链接。

原理、架构说明、教程、基准测试和调研结果可作为用途参考，
不要求每份文档严格归类，也不为这些类别预建空目录。

## 新增与拆分

1. 先检查已有文档：属于同一阅读任务的内容，优先补充到已有主题。
2. 内容形成独立任务、读者或上下文时，再新建文件，使用能表达主题的文件名。
3. 从相关入口添加链接，说明阅读条件；无需在每个入口重复登记同一专题。
4. 同类主题增长到难以查找时再归组，拆分后更新原有引用。

每个事实或详细规则只维护一个权威位置。其他文档可以给出必要的短概述，
并链接到详细说明；避免重复维护完整命令表、配置步骤或模块职责表。
命令参数与依赖版本以任务文件、manifest 等配置为准，文档解释用途、边界和取舍。

## 轻量写作

- **范围清楚**：标题与开头说明本文解决什么问题，让读者判断是否需要继续阅读。
- **状态清楚**：区分当前实现、目标设计和待验证结论；讨论示例不自动成为现有 API。
- **示例可信**：可运行示例给出必要前提与执行位置；伪代码、接口草案明确标注。

手写 Markdown 通常控制在 200 行以内，普通正文单行尽量不超过 100 字。
这两个数是结构检查的提醒值，不是硬门槛；链接、表格和代码以可读、可复制为准。
超出时先检查是否混合了独立主题，按阅读任务拆分，不为满足数字机械分文件或合并长行。

## 随改动维护

- 改变文档已描述的行为、命令或模块边界时，在同一次改动中同步相关说明。
- 不要求每次代码改动都增加文档；只更新受影响的内容。
- 新增、移动或删除文档时，检查入口和相对链接，清理失效内容。
- 记录验证结果时说明范围与限制，不把构建通过或一次实测扩大为普遍保证。
